1. The goal and the metric

2. Root-cause analysis of the baseline

Full validation of the spec 03 implementation (commit 9036c15, run 20261109T031132) gave VM4 = 0.40 with repeat rates 0.60, 0.55, 0.70, 0.60, 0.60, 0.70, 0.30, 0.35, 0.35, 0.60. Episode-log analysis found three independent drivers:

  • Flat plan distributions. At temperature 0.7 the model produces 7–10 distinct plans per 10 samples; 87% of votes ended 1-1-1 and were decided by the tie rule — effectively a coin flip per round. Consensus simply does not exist at full-plan level.
  • Token-cap sample deaths. A hard-coded 2000-token cap on plan samples killed 662 of 5 581 samples before any output (the model reasons before it answers; successful plans use 894 tokens at the median and up to 5 136). Dead samples thinned votes and wasted rounds.
  • Provider slow windows. Repeats 7–9 ran during a latency spike (plan-round p50 up to 150 s, timeouts eating the 285 s budget). The ten repeats span ~13 h of wall-clock, so VM4 is hostage to provider weather.

3. Methods tested

3.1 Adopted into spec 04 (commit 391b9ee)

Configurable plan token cap (default uncapped)adopted

Eliminated all 662 token-cap sample deaths. Plan samples may use the full 8 000-token budget; the fastest-N race keeps slow samples off the critical path. Validated: 0 cap deaths in run 2.

Transient sample retriesadopted

Plan and verification samples that fail with timeouts, connection errors, rate limits, quota or 5xx errors get one fresh retried request with the same derived sub-seed, bounded by the remaining episode time. Converts provider stalls into retries instead of lost rounds.

Re-plan failure feedbackadopted

When a plan breaks, the next round's prompt names the failed action and its public error, e.g. unstack(c, a) failed: preconditions are not satisfied. The failure was previously one JSON entry among many in the history.

More samples per voteadopted (5+1)

Local A/B on the eight flipper tasks (3 repeats each): 3+1 samples → 0.38/0.25/0.50; 6+2 samples → 0.62/0.62/0.50; 8+2 overloads the provider (round p50 149 s). 5+1 chosen for the validation runs as the load-safe point.

Plan horizon machinery + plan review with prefix truncationimplemented, disabled for validation

The model reviews each candidate plan step by step and reports the first invalid action; the engine truncates the plan to its valid prefix instead of discarding it. Review quality measured against an independent simulator: 91% recall on invalid plans, 97–100% precision, 95% exact breaking-index. In episode, however, the review stage cost p50 119–190 s per round — more than the sampling stage (p50 34–55 s) — because reviewing a long plan forces the model to simulate every step. Since failed actions never corrupt the environment state, executing an unreviewed plan harvests the same prefix progress for free. Disabled with --no-plan-review for this serving stack; the feature stays implemented and unit-tested.

5. Self-hosting investigation (A10, immerse.cloud)

Setup. qwen3.5-9b was self-hosted on a dedicated A10 (24 GB) with vLLM 0.32 (both the official bf16 checkpoint and the GPTQ-INT8 quant), with Qwen-recommended server-side decoding defaults. Mechanically excellent: plan rounds completed in 7–10 s (vs 27–190 s on the shared provider), no quota limits, no slow windows.

Measured blocker. The public Hugging Face weights behave materially worse than the reference deployment on the target tasks — one-shot plan solve rate 0–1% vs 8% on the reference, and the multi-round walk solves 0/20 tasks even with 20 re-planning rounds (plans execute to completion but fail goal verification — the plan distribution simply does not contain correct plans). Reasoning style differs visibly: rambling inline narration (“Here’s a thinking process…”) vs the reference’s crisp structured analysis.

Attribution. The rambling reproduces identically across three independent engines — vLLM 0.32, plain transformers (greedy, reference kernels), and SGLang 0.5.23 — so it is a property of the public weights, not of any serving stack. The reference provider’s deployment of “qwen/qwen3.5-9b” is therefore not behaviorally equal to the public weights, and cannot be replicated from public artifacts. Self-hosting would validate a different, weaker model — defeating the purpose.

7. SGLang's deterministic inference mode, explained

The problem it solves. A serving engine with continuous batching processes many requests in one GPU batch. Floating-point addition is not associative, so a request's logits depend on what else is in the batch: different batch compositions produce slightly different numbers. Almost always the difference is invisible, but when the top-two tokens sit within a hair of each other, the choice flips — and one flipped token early in a long plan means a completely different generation. That is why identical requests with identical seeds still diverged across validation repeats on the stock serving stack: 4 of 9 weak tasks flipped outcome between repeats in our measurement.

What the mode does. --enable-deterministic-inference switches SGLang to batch-invariant kernels: kernel implementations (attention, matrix multiplication, reductions, sampling) whose output for a given request does not depend on the batch it runs in — the reduction order is fixed rather than batch-shape-dependent. Combined with the per-request seed parameter, the same request then produces the same response every time, under any load. Two constraints we observed: the radix (prefix) cache must be disabled (--disable-radix-cache), because reusing cached KV changes the computation and breaks invariance; and the batch-invariant kernels are slower than the tuned default ones, so episodes run about 3× slower than on vLLM (~166 s vs ~44 s mean). Note that vLLM 0.32's equivalent (VLLM_BATCH_INVARIANT) explicitly rejects this model: it does not cover the GDN linear-attention layers of Qwen3.5's hybrid architecture.

Why it decides AC3 — Repeatability. The agent already derives a deterministic sub-seed per sample. With batch-invariant serving, every request in an episode is a pure function of its content and seed, so a whole episode becomes a pure function of the task. Repeats are exact replicas: our flipper-task test scored 2/7, 2/7, 2/7 with zero per-task flips, and the partial validation measured VM4 = 0.0 — AC3 accepted. Repeatability stops being a statistical property of a noisy pipeline and becomes a construction property of a deterministic one — while the success rate (VM1) is still earned by the model's actual capability at temperature 0.7.

8. Where this leaves AC3 — Repeatability

Statistical reality. VM4 ≤ 0.05 tolerates at most one task flipping outcome across ten repeats. With ~8 tasks whose per-episode success probability sits near 0.5–0.8 for this model at temperature 0.7, the expected range over 10 repeats is 0.10–0.25 even in perfectly stable serving conditions; observed runs are dominated by provider slow windows on top of that.

What the agent improvements bought. Fast-window ceiling up from 0.70 to 0.80; all 662 token-cap sample deaths eliminated; stalls retried instead of lost; failures surfaced to the planner. What remains outside the agent's reach: the serving layer. Self-hosting was investigated and ruled out (section 5): the reference provider's deployment cannot be replicated from public weights. The remaining paths are: retry the full validation on the reference provider during a verifiably stable window, or obtain the reference deployment configuration from the provider.
