01 · The accepted solution

Model proposals become a learned, verifiable planner.

The model does not need to produce a correct plan on every sample. Successful actions teach the engine reusable public transition rules; once enough rules exist, ordinary search supplies the remaining plan.

1

Bootstrap with model plans

Sample five complete plans plus one spare. Vote on the first action, retain the selected complete plan, and execute it one action at a time. Existing transient retries remain active.

2

Learn from each observation

Compare exact public states before and after every successful action. Generalize added and deleted predicates through the action’s argument positions. Observed consumed facts become conservative preconditions.

3

Search the learned rules

When enough rules are known, bounded breadth-first search finds a shortest remaining plan from the current public state to the formal goal. No model request is needed for this plan.

4

Verify the actual goal state

Exact grounded goal predicates are checked against the latest public state after every action. Completion is immediate when all goals hold; missing goals continue execution or recovery.

Rule conflict or unsupported input
Prediction mismatches disable the unsafe rule and its remaining tail. Unsupported goals or observations retain model verification and model planning.
↻
Missing rule after permanent failure
Transition tabu prevents known repeats. Bounded exploration may probe one untried unknown-rule action, then learning and search resume.
Why repeatability improved: sampling is still free, but success no longer depends on repeatedly drawing a complete correct plan. Correct observed rules support deterministic shortest-path recovery, while exact goal evidence prevents both premature completion and acting after the goal is reached.
02 · What the engine learns

A public observation becomes a reusable action rule.

This example shows the core mechanism. The same construction applies to every successful single-action transition in the episode.

Observed public transition
Before(clear a) · (on-table a) · (hand-empty)
Actionpick_up(block=a)
After(holding a)
Learned generalized rule 
preconditions:
  (clear {block})
  (on-table {block})
  (hand-empty)

delete effects:
  (clear {block})
  (on-table {block})
  (hand-empty)

add effects:
  (holding {block})

Search composes these learned rules

After learning the relevant rules from public observations, generic search can derive a remaining plan such as:

unstack(b, c) → put_down(b) → pick_up(c) → stack(c, a)

The sequence is illustrative. Production code does not branch on restack_bca, block names, or any other task identity; it searches only the rules and formal state available in that episode.

03 · Why C28, specifically, crossed the boundary

Two residual fixes completed the already strong C27 learner.

C27 had transition learning but completed with 197/200 successes and strict VM4 rejection. Its three failures identified the exact final changes.

C27 failure

Two missing-rule timeouts

Two restack_bca episodes never observed a successful unstack, so learned search could not construct a recovery plan.

C28 fix

Bounded unknown-rule exploration

After a permanent action failure, C28 can probe an untried unknown-rule action. It skips learned, rejected, tried, failed, and schema-invalid transitions, with candidate and deadline bounds.

C27 failure

One goal-state final-delivery miss

A tower_four episode reached the exact goal, but a pending-write race caused final delivery to be skipped.

C28 fix

Correct write-done ordering

The I/O thread now marks the write complete before scheduling future completion, preventing the final-delivery check from observing a false pending write.

05 · Scope and boundaries

What the accepted mechanism does—and does not assume.

General-purpose and public-only

  • No task-ID dispatch, reference plans, private evaluator results, or cross-episode learned memory.
  • Rules are learned independently in each episode from public task input, tools, actions, and observations.
  • Model sampling remains stochastic. C28 explicitly omits provider seeds and does not use deterministic-serving modes.
  • Unsupported formal goals or observations fall back to model planning and verification.

Deliberate limitations and guards

  • Formal checking supports grounded conjunctive PDDL goals and complete public state snapshots.
  • Learned preconditions use observed consumed facts; persistent preconditions are not inferred. This is not claimed to be a sound general PDDL planner.
  • Prediction conflicts disable rules and tails. Search excludes observed failures and is bounded by states, remaining actions, and deadline.
  • Learned planning and exploration require complete-plan execution; horizon-controlled prefixes retain model planning.
