02

What AC3 measures

One task changing outcome can consume the entire acceptance margin.

For each unperturbed repeat, the validator computes the overall success rate across the same 20 tasks. VM4 is the largest repeat rate minus the smallest.

VM4 = max(repeat success) − min(repeat success)accept if VM4 ≤ 0.05
20 tasks per repeatEach task contributes 0.05 to one repeat’s overall success rate.
One-task marginAll repeats must fit within a one-success difference, subject to floating-point comparison.
Partial ≠ accepted projectModified configurations are diagnostic even when all 20 tasks and 10 repeats are used.
Floating point matters. The validator strictly compares the computed floating-point difference. For example, 0.65 − 0.60 evaluates to 0.050000000000000044, which is rejected even though the mathematical difference is 0.05.
03

The decision-flow changes

Consensus is enforced by the engine, while the model still produces ordinary complete plans.

H — execution horizon.
Caps the candidate actions retained for execution. Truncated candidates become non-reaching.
V — vote horizon.
Caps only the actions compared by voting. V=1/H=2 combines first-action consensus with two-action execution.
Prompt horizon — independent.
The model can still return complete plans; the engine does not rely on short-horizon instruction compliance.

Empty-plan control

Before the first observation, actionable valid candidates suppress empty completion claims. Empty-only rounds can still verify an initially satisfied objective. The successful H=1 screen suppressed 68 empty claims.

Race-independent completion

Candidates sharing a normalized prefix must unanimously claim completion. The rule survives goal-review filtering and reversed race-completion order, preventing a fast sample from deciding verification semantics.

06

What did not work

Negative results prevented repeated spending on mechanisms that looked plausible but failed in episodes.

Aborted

Prompt-controlled H=1

All five initial candidates were empty on easy tasks. No prefix truncation occurred, so the run did not test the intended mechanism.

Rejected

Selected-prefix review

Repeats fell to 0.40 and 0.30. Even short post-vote reviews rejected trajectories the environment could use for progress.

Mixed

Goal regression

H=2 gave 0.70 / 0.70 / 0.50. H=1 gave 0.60 / 0.60 / 0.70. These short-screen values did not establish 10-repeat durability.

Rejected

More budget or more samples

50 actions / 298 seconds produced 0.70 / 0.60. Split 4+1 samples produced 0.80 / 0.55. Both were stopped after definitive rejection.

Operational

Prefix caching and CUDA graphs

Performance changes did not stabilize AC3. A separate 3+1 screen passed AC3 but exposed stderr-driven final-response loss.

Fixed operationally

Error-only logging

Thirteen missing finals were caused by the 64 KiB stderr limit, not slow episodes. --log-level ERROR restored AC7 to 1.0; VM4 remained 0.15.

Rejected offline

Model-compiled predicate search

Only 8/21 generic search plans reached the goal. restack_abc, stack_three, and tower_four were 0/3; model-supplied transition semantics were not reliable enough.

Rejected offline

Invariant-ledger prompt

Invariant/resource bookkeeping produced 6/40 solving samples versus 3/40 for goal regression, but both voted only 1/8 tasks. The raw increase did not justify implementation or episodes.

Rejected offline

Direct next-action voting

With output names constrained to public tools, only stack_ab had an optimal voted first action. All three restack votes were invalid pickups; no episodes were spent.

Efficient partial validation. Earlier screens used all 20 tasks and three unperturbed repeats with only AC1/AC3/AC6/AC7. C19 used the 14 non-saturated tasks to test recovery mechanisms; offline probes rejected weaker ideas without episodes. Prompt variants and failure scenarios were omitted from experiments. Completed-repeat bounds enabled early stopping whenever a 10-repeat VM4 threshold became mathematically unrecoverable.
